## Full Summary

Extends iter1's W-TinyLFU cache-admission simulator (imported unchanged as iter1_method.py) with two targeted additions. Part A is the sharpest possible disconfirmation test of the hypothesis: at the win-corner cell (ratio=0.01, alpha=1.2, cache_capacity=1500, key_space=150,000), it sweeps very short global-reset multipliers (1x, 2x, 4x cache capacity, in addition to iter1's already-swept {4,8,16,32}) across all 4 drift scenarios (low/high magnitude x low/high frequency rank reshuffles), 3 seeds each, asking whether a cheaply-shortened global reset closes the recovery-time gap with the proposed per-key CoV-decay estimator without any per-key machinery. For each scenario it identifies the best short-reset arm and compares its mean recovery time against iter1's already-computed proposed-estimator result (loaded directly from iter1's full_method_out.json, not rerun) for a genuine head-to-head. Result: the proposed per-key-decay estimator still recovers faster than the best short-reset baseline in 3 of 4 scenarios (low_mag_high_freq: proposed 14% faster; high_mag_low_freq: proposed 8% faster; high_mag_high_freq: proposed 6% faster), and is statistically tied (short reset ~9% faster, within seed noise) in the fourth (low_mag_low_freq) -- so short reset does not substitute for the per-key mechanism at this cell, though the margin narrows for infrequent, low-magnitude drift. Part B replays both estimators end-to-end over the real Twitter production trace (twitter/cache-trace cluster026, 80,000 requests, 67,681 distinct keys, sourced pre-decoded as JSON from this iteration's dataset dependency, unlike iter1 which could not obtain a lightweight decoder and skipped the real-trace arm entirely), string keys mapped to dense int ids for the shared sketch/SLRU code, cache capacity matched to the same 0.01 ratio (677 slots), baseline multiplier tuned fresh on the real trace itself via a single-pass sweep over {4,8,16,32}. On real traffic the baseline achieved final hit ratio 0.042 (memory 39,985 bytes) versus per-key-decay 0.028 (memory 185,167 bytes) -- both far lower than synthetic hit ratios because a single 80k-request trace with 67,681 distinct keys is heavily compulsory-miss dominated, and per-key-decay underperforms baseline here, a real-traffic caveat worth flagging rather than hiding. A lightweight unsupervised JS-divergence changepoint detector (rolling top-50 key-identity distributions, window=2000, stride=500, 95th-percentile threshold) was first validated against KNOWN drift events on a synthetic trace (recall=1.0, precision=0.67, 8/8 true events matched) before being applied to the unlabeled real trace, where it surfaced 8 candidate changepoints with recovery-time-at-changepoint reported for both estimators, explicitly caveated as coarse and unsupervised rather than ground truth. All code reuses iter1's CountMin4Bit sketch, Doorkeeper, GlobalResetFrequencyEstimator, PerKeyDecayFrequencyEstimator, SLRUCache, WindowTinyLFUCache, make_zipf_drift_trace, run_trace, and compute_recovery_times classes/functions completely unchanged via direct import, isolating any result differences to the new sweep points and the real-trace data source rather than implementation drift.
